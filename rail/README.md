# 리니어 스테이지 (스텝모터 + 볼스크류)

라즈베리파이 GPIO로 스텝모터 드라이버에 펄스를 보내 캐리지를 mm 단위로 움직인다.

| 파일 | 역할 |
| --- | --- |
| `pulse_test.py` | 배선 확인용. 200펄스만 보내 1.25mm 정도 움직여 본다 |
| `stage.py` | mm 단위 제어. 소프트 리밋 포함 |

## 하드웨어

| 항목 | 모델 |
| --- | --- |
| 스테이지 | LSM4-NK235630x-**1610** |
| 드라이버 | MSD-224 |
| 모터 | 1.8도 2상, **3A/phase** |
| 전원 | 24V 5A (HT-AD036) |

### 리드 — 가장 중요한 값

모델명 뒤 4자리가 리드(1회전당 이동 거리)를 결정한다. **이 값이 틀리면 이동
거리가 통째로 어긋난다.**

| 모델 뒷자리 | 스크류 | 리드 | 매뉴얼 최대 속도 |
| --- | --- | --- | --- |
| -1605 | φ16 | 5 mm | 50 mm/s |
| **-1610** | **φ16** | **10 mm** | **100 mm/s** |
| -1620 | φ16 | 20 mm | 200 mm/s |
| -1204 | φ12 | 4 mm | 40 mm/s |

이 프로젝트는 **-1610 (리드 10mm)** 이고, `stage.py` 에 그렇게 설정돼 있다.

분주 1/8 기준으로 `1mm = 160 스텝` 이 된다.

```
STEPS_PER_MM = STEPS_PER_REV × MICROSTEP ÷ LEAD_MM
             = 200 × 8 ÷ 10 = 160
```

## 드라이버 DIP 스위치 (⚠️ 전원 끈 상태에서)

MSD-224 좌측면에 S1~S6 스위치가 있다. 옆면에 설정표가 인쇄돼 있으니 그것을 보고
맞춘다.

### 전류 (S4, S5, S6)

모터 정격이 **3A/phase** 다. 드라이버는 4A까지 가능하지만 **정격을 넘기면 모터가
탄다.**

- 정상 운용: **2.8 ~ 3.0A**
- 처음 테스트: **2.0A** 로 낮게 시작하는 편이 안전하다 (발열이 적다)

### 분주 (S1, S2, S3)

**1/8 (1600 pulse/rev)** 로 설정한다. `stage.py` 의 `MICROSTEP = 8` 과 일치해야
한다.

분주가 낮으면(1/2) 진동과 소음이 크고, 너무 높으면(1/32) 같은 속도를 내는 데
펄스를 훨씬 많이 쏴야 해서 속도가 안 나온다. 1/8이 균형점이다.

## 배선 (⚠️ 전원 완전히 뽑은 상태에서)

### ① 모터 → 드라이버

| 모터선 색 | MSD-224 단자 |
| --- | --- |
| 🔴 빨강 | `A +` |
| 🟢 초록 | `A −` |
| 🟡 노랑 | `B +` |
| 🔵 파랑 | `B −` |

같은 상(A 또는 B)의 두 선을 서로 바꾸면 회전 방향이 반대가 된다. 상을 섞으면
(예: 빨강과 노랑을 바꿈) 모터가 소리만 내고 돌지 않는다.

### ② 전원 → 드라이버

```
24V 어댑터 → DC잭 케이블 → 🔴 빨강 = VCC(+)
                          ⚫ 검정 = GND(−)
```

MSD-224 아래쪽 `VCC` / `GND` 단자에 연결한다.

### ③ 라즈베리파이 → 드라이버 (신호)

| MSD-224 | 파이 GPIO | 물리핀 |
| --- | --- | --- |
| `PUL +` | GPIO 22 | 15 |
| `PUL −` | GND | 6 |
| `DIR +` | GPIO 27 | 13 |
| `DIR −` | GND | 9 |
| `ENA +` | GPIO 17 | 11 |
| `ENA −` | GND | 14 |

> **ENA는 생략해도 된다.** 연결하지 않으면 모터가 항상 여자(힘이 들어간) 상태로
> 유지된다. 처음에는 **ENA 2가닥을 빼고 4가닥으로만** 배선하는 편이 단순하고
> 문제도 적다. 생략할 경우 `stage.py` 의 `ENA_PIN = None` 으로 바꾼다.

## 전원 켜기 전 점검 ✋

1. ⚠️ **24V 계통이 라즈베리파이 쪽에 하나도 닿지 않았는지** 확인. 닿으면 파이가
   즉시 망가진다. 두 계통이 공유하는 것은 GND뿐이다
2. 모터선 4가닥이 서로 닿아 있지 않은지
3. 나사단자가 모두 조여져 있고 점퍼핀이 헐겁지 않은지
4. **캐리지를 손으로 돌려 스트로크 중앙에 둔다.** 리미트스위치가 없으므로
   끝단까지 가면 그대로 부딪힌다. 어느 쪽으로도 여유가 있는 자리에서 시작할 것
   (`stage.py` 는 위치를 모르는 상태로 시작하므로, 보정하거나 위치를 알려줘야
   움직인다)
5. 파워코드 → 어댑터 → 콘센트 순으로 연결

전원을 넣으면 드라이버 LED가 켜지고 모터에서 "지-잉" 하며 힘이 들어간 느낌이
나면 정상이다. **빨간 알람 LED가 켜지면 즉시 전원을 빼고** 배선을 다시 확인한다.

## 소프트웨어 준비

```bash
sudo apt update
sudo apt install -y python3-lgpio
```

데몬도 루트 권한도 필요 없다. `/dev/gpiochip0` 의 그룹이 `dialout` 이고
기본 사용자가 거기 속해 있어서 그대로 쓸 수 있다.

### pigpio 가 아닌 이유

`pigpio` 는 이런 용도의 표준이지만 **Ubuntu 24.04 arm64 에는 데몬이 없다.**
클라이언트 패키지(`python3-pigpio`, `pigpio-tools`)만 저장소에 있고, 정작 핀을
흔드는 `pigpiod` 가 빠져 있다. 칩 레지스터를 직접 다루는 코드라 32비트
라즈베리파이용으로만 빌드되기 때문이다. Raspberry Pi OS 에는 있다.

`lgpio` 는 커널의 GPIO 캐릭터 장치를 거치므로 칩 종류를 타지 않고 Pi 5 에서도
동작한다. 대신 타이밍이 커널 스케줄링에 의존해서 고속에서 펄스 간격이 흔들린다.
그래서 `MAX_SPEED_MM_S` 를 20mm/s(3.2kHz)로 낮춰 두었다. 더 빨라야 하면
`pigpio` 를 소스에서 빌드해 `_send_pulses()` 만 갈아끼우면 된다.

## mm 단위 제어

```bash
python3 stage.py
```

```python
from stage import move_mm, move_to_mm, position_mm, set_position_mm

move_mm(10, speed_mm_s=5)   # 정방향 10mm
move_mm(-10)                # 역방향 10mm
move_to_mm(50)              # 절대 위치 50mm
print(position_mm())
```

처음에는 `speed_mm_s=5` 정도로 시작하고, 안정되면 조금씩 올린다. 갑자기 고속을
주면 **탈조**(스텝 씹힘)가 나면서 "삐-익" 하고 멈추고, 그 순간 실제 위치와
소프트웨어가 아는 위치가 어긋난다.

`MAX_SPEED_MM_S = 100` (모델 -1610 스펙)을 넘는 속도는 거부한다. 그래도
탈조가 나면 속도를 더 낮추거나 가감속(ramp) 로직이 필요하다.

## ⚠️ 리미트스위치가 없다

현재 구성에는 끝단 감지 센서가 없어서, **소프트웨어만이 스테이지의 끝을 안다.**
펄스를 계속 보내면 캐리지가 끝단에 부딪혀 갈리고 볼스크류나 모터가 손상된다.

코드에 걸어 둔 방어:

- `STROKE_MM` 범위를 벗어나는 이동은 `SoftLimitError` 로 거부
- **위치를 모르는 상태로 시작한다.** 임포트 직후에는 어떤 이동도 거부되고,
  보정하거나 `set_position_mm()` / `resume_position()` 으로 알려줘야 움직인다
- 이동 중 중단되면(Ctrl+C 등) 몇 펄스가 나갔는지 알 수 없으므로 위치를 미상으로
  되돌린다
- `MAX_SPEED_MM_S` 초과 거부

테스트 중에는 항상 전원 플러그 근처에 손을 두는 것이 좋다. 여유가 되면
리미트스위치를 다는 편이 안전하다(스테이지에 장착 구멍이 있다). 스위치가
있으면 원점을 기계적으로 찾을 수 있어서 아래 보정 절차가 필요 없어진다.

## 보정 — 양 끝을 사람이 지정한다

리미트스위치가 없으므로 원점을 기계적으로 찾을 수 없다. 대신 **사용자가 양 끝
지점을 직접 지정**하고, 그 사이 거리를 유효 스트로크로 삼는다.

핵심은 **보정 중에는 절대 위치가 필요 없다**는 점이다. 상대 이동만 쓰기 때문에
"위치를 알아야 움직이는데 움직여봐야 위치를 안다"는 순환을 피한다.

```python
begin_calibration()          # 지금 자리가 기준(0)
jog_mm(10, speed_mm_s=5)     # 반대쪽 끝까지 조금씩. 미세조정은 0.5mm 씩
...
end_calibration()            # 지금 자리를 반대쪽 끝으로 확정 → 저장
```

`cancel_calibration()` 으로 버릴 수 있다. 버리면 스트로크는 그대로 두고 위치만
미상으로 되돌린다.

뒤로 움직여서 끝냈다면(변위가 음수) 지금 자리가 더 낮은 쪽이므로 **그쪽이 0**이
된다. 즉 0 은 항상 두 지점 중 좌표가 낮은 쪽이고, mm 는 정방향으로 증가한다.

⚠️ **보정 중에는 끝단 충돌을 막아 주는 것이 아무것도 없다.** 스트로크를 모르니
소프트 리밋을 걸 수가 없다. `CALIB_MAX_TRAVEL_MM`(2000mm) 누적 감시가 폭주만
잡을 뿐이다. 눈으로 보며 소리를 듣는 것이 유일한 방어다.

리미트스위치를 달면 이 구간 자체가 사라진다.

일반 이동(`move_mm`)은 보정 중에 거부된다.

### 저장되는 값

`rail/calibration.json` 에 남는다. 서버를 껐다 켜도 유지된다.

```json
{
  "stroke_mm": 287.5,
  "steps_per_mm": 160.0,
  "position_mm": 143.2,
  "calibrated_at": "2026-08-23T16:40:00+09:00",
  "calibration_id": "3f9c1a7e5b2d4e08a1c6f0b93d7e2415",
  "saved_at": "2026-08-23T18:12:04+09:00"
}
```

`calibration_id` 는 보정할 때마다 새로 발급된다. 스테이션 좌표가 어느 보정
기준인지 대조하는 데 쓴다. 시각만으로는 같은 초에 두 번 보정한 경우를 구분하지
못해서 낡은 좌표를 놓친다.

`steps_per_mm` 을 같이 적는 이유는, `LEAD_MM` 이나 `MICROSTEP` 을 바꾸면 저장된
mm 값이 더 이상 같은 뜻이 아니기 때문이다. 불일치하면 보정값을 무시하고 경고를
찍는다. 그때는 다시 보정해야 한다.

파일은 `.gitignore` 에 있다. 장비마다 값이 다르므로 커밋하지 않는다.

### ⚠️ 스트로크는 신뢰하지만 위치는 신뢰하지 않는다

| | 재시작 후 |
| --- | --- |
| `stroke_mm` | 그대로 쓴다 — 하드웨어 특성이라 변하지 않는다 |
| `position_mm` | **불러오되 믿지 않는다** |

전원이 꺼진 사이 캐리지를 손으로 밀 수 있기 때문이다. 저장돼 있다는 것만으로는
실제 위치의 근거가 되지 못한다. 그래서 재시작 후 첫 이동 전에 한 번 확인한다.

```python
resume_position()      # 안 건드렸다 — 저장된 값을 그대로 이어 쓴다
set_position_mm(120)   # 건드렸다 — 실제 위치를 새로 알려준다
```

번거롭지만, 이 확인이 없으면 재시작할 때마다 조용히 틀린 위치에서 움직이게 된다.

## 속도 상한은 왜 30mm/s 인가

스테이지 매뉴얼상 -1610 은 100mm/s 까지 가능하지만, 실제 한계는 다른 데서
걸린다. 실측 결과 병목은 예상과 달랐다.

| 후보 | 실측 | 병목? |
| --- | --- | --- |
| `lgpio` 타이밍 | 16kHz(100mm/s)까지 오차 **+1.4% 로 일정** | ❌ |
| 모터 기동 주파수 | **40mm/s 성공 / 50mm/s 탈조** | ✅ |

`lgpio` 오차가 속도와 무관하게 일정하다는 것은 지터가 아니라 호출 오버헤드라는
뜻이다. 소프트웨어는 100mm/s 도 만들어낸다.

진짜 문제는 **가감속이 없다**는 것이다. 정지 상태에서 곧바로 목표 속도로 펄스를
쏘기 때문에, 모터의 기동 주파수를 넘으면 첫 스텝부터 탈조한다.

기동 주파수 한계는 부하·모터 온도·전원 전압에 따라 움직인다. 탈조는 소프트웨어가
감지할 수 없어 조용히 위치만 어긋나므로, 경계(40)에 붙이지 않고 25% 여유를 두어
**30mm/s** 로 잡았다.

더 빠르게 하려면 속도를 올릴 게 아니라 **가감속 램프**를 넣어야 한다. 낮은
주파수로 출발해 서서히 올리면 기동 주파수 제약이 사라지고 기계적 상한까지 쓸 수
있다.

## 구현 메모

펄스는 `lgpio` 의 `tx_pulse()` 로 만든다. `pulse_cycles` 로 보낼 펄스 수를 직접
지정하므로 실제로 나간 스텝 수가 보장된다. 주파수만 지정하는 방식은 요청 주파수를
샘플레이트 기준 이산값으로 스냅시키기 때문에, 요청값으로 계산한 시간만큼
기다리면 실제로 나간 펄스 수가 어긋나고 왕복할수록 오차가 누적된다. wave는
보낼 펄스 수를 직접 지정하므로 스텝 수가 보장된다.

**아직 실제 하드웨어에서 검증하지 않았다.** 모터를 물린 뒤 `pulse_test.py`
부터 확인할 것.
